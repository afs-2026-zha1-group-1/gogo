## Intent

Let an organizer grow the trip beyond its creator: one link (or its QR) carries
the invitation, the invitee sees enough to recognize the trip before committing,
and acceptance is explicit, single, and bounded by the main-plan confirmation
gate. A broken or unknown link must fail closed: a generic message, never private
trip data, never a membership.

## Actors and boundaries

The `X-User-Id` header remains a **scaffold-level stand-in for authentication**
(REQ-003 §Actors): trusted without verification, never a security control.
Issuance and acceptance are identity-bound; the invitation preview is bound to
the token alone, because the link itself is the organizer's share act.

Boundary ownership: the backend owns `trip_invitation`, the `trip` main-plan
state column, and all four endpoints. The frontend owns the invitation panel,
the join page and their states; it composes the absolute invitation URL from its
own origin and never decides membership or closure itself. The `trips`
capability keeps ownership of the trip aggregate; REQ-004 adds one state
requirement to it and reads membership through it.

## In scope

- Flyway migration `V3__create_invitation.sql`: `trip_invitation` table and the
  `trip.main_plan_confirmed` state column (default unconfirmed).
- `POST /api/trips/{id}/invitation` — organizer-only get-or-create of the trip's
  single invitation; returns token and join path.
- `GET /api/invitations/{token}` — public preview: trip name, destination, start
  and end dates, and whether joining is still open; nothing else.
- `POST /api/invitations/{token}/accept` — identity-bound explicit acceptance;
  idempotent membership; rejected after main-plan confirmation.
- Unusable-invitation behavior for unknown tokens on both preview and accept.
- Frontend: invitation panel on the trip details surface (link, copy action, QR
  encoding the same absolute URL), join page at the token route (preview, accept,
  joined state), and the generic unusable state; required loading/error/permission
  states even where not pictured.
- Backend acceptance tests and verification documents for the new endpoints.

## Out of scope

- Main-plan confirmation flow itself (US-037, issue #16): no endpoint or UI sets
  the state in this change; tests set it directly in the database.
- Invitation revocation, expiry configuration, native/social sharing fallback
  (US-008 design scope marks them optional); the unusable page must not promise
  them.
- Notification workflow behind the pictured "remind organizer" action (US-012
  design scope).
- Member listing/management (US-013), preferences (US-019+), plan generation
  (US-031+), dashboard (US-061).
- Real authentication; `X-User-Id` stays trusted as given.
- Multiple concurrent invitations per trip, invitation analytics, link clicks.
- ORM, i18n, CI job structure changes.

## Scenarios and AC hints

| id | Scenario | Observable outcome |
|---|---|---|
| I1 | Alice (`X-User-Id: 1`), organizer of the fixture trip with unconfirmed main plan, obtains an invitation | `200` with a token and join path; one `trip_invitation` row for the trip; the join path opens a joinable invitation for "Singapore Friends Day" |
| I2 | Alice obtains again | `200` with the same token; still exactly one invitation row |
| I3 | Ben (`X-User-Id: 2`), member but not organizer, requests an invitation | `403` with `code = NOT_ORGANIZER`; no invitation row created |
| I4 | Issue request without `X-User-Id` (or an unknown id) | `401` with `code = USER_REQUIRED`; nothing created |
| I5 | Issue request for a trip id that does not exist | `404` with `code = TRIP_NOT_FOUND` |
| I6 | Eve scans the QR rendered next to the link | Decoded URL equals the copied absolute link; opening it exercises J1–J4 rules (E2E) |
| J1 | Eve (`X-User-Id: 5`), non-member, previews a valid token while the main plan is unconfirmed | `200` with name `Singapore Friends Day`, destination `Singapore`, dates `2026-12-05`/`2026-12-05`, joining open; no member list, itinerary or preference data |
| J2 | Eve accepts the valid invitation | `200` joined; a `trip_member` row (trip, 5) exists; `GET /api/trips/{id}` as Eve now returns `200` |
| J3 | Eve submits acceptance twice under the same identity | Both responses report joined; exactly one `trip_member` row for (trip, 5) |
| J4 | Main plan confirmed (test-only state set), Eve not a member, accepts | `403` with `code = JOINING_CLOSED`; member list unchanged |
| J5 | Accept without `X-User-Id` (or an unknown id) | `401` with `code = USER_REQUIRED`; no membership |
| U1 | Eve previews a token that refers to no invitation | `404` with `code = INVITATION_NOT_FOUND`; generic unusable message; no trip values |
| U2 | Eve accepts a token that refers to no invitation | `404` with `code = INVITATION_NOT_FOUND`; no membership created |
| U3 | Join page opened with an invalid token | Unusable surface renders the generic message and no private field; back-home action available (E2E) |

Reverse cases for non-goals: no endpoint sets `main_plan_confirmed` (R-1); no
revocation or expiry endpoint exists (R-2); preview and accept of an invalid
token return no trip field values (U1/U2 double as the privacy reverse case).

Every error response carries a stable machine-readable `code`; human-readable
messages are implementation text, not contract.

## Constraints

- React frontend, Spring Boot / Java backend, embedded SQLite, Flyway — unchanged
  stack (`TODO.md`, REQ-001).
- No ORM; `JdbcTemplate`.
- Dates ISO-8601 `YYYY-MM-DD`; the Asia/Singapore test context does not affect
  date-only values.
- Depends on REQ-003's `V2` tables (`app_user`, `trip`, `trip_member`) and its
  identity contract; REQ-003 P4 must land before REQ-004 P4.
- Repository documentation in English (`AGENTS.md`); two-job CI reused unchanged.
- UI follows `ui-design-reference/` style (screens 04/05/06); QR must encode the
  real URL, not a decorative pattern.

## Affected capabilities

- New capability `invitations`, four ADDED requirements: invitation issuance,
  invitation preview, invitation acceptance and joining, unusable invitation.
- `trips`: one ADDED requirement "Trip main-plan confirmation state" (state
  column, default unconfirmed, no mutation path in this change).
- `greeting` untouched.
