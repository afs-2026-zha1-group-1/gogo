## Intent

Give a group a shared, persisted space for one journey: the creator names it, sets
where and when, and everyone listed as a member can open the same record and see
exactly what was saved. Iteration 0 needs the write and the read of the same
aggregate to be demonstrably correct against a real database.

## Actors and boundaries

The `X-User-Id` header is a **scaffold-level stand-in for authentication**. The
backend trusts the header without verifying it; it exists so membership can be
decided and tested before any identity system is in scope. It must not be
described as a security control, and it must not be extended into a general
authorization mechanism inside this change.

Boundary ownership: the backend owns the `trip`, `trip_member` and `app_user`
tables and both endpoints. The frontend owns form state, rendering and error
presentation, and never decides membership itself.

## In scope

- Flyway migration `V2` creating `app_user`, `trip`, `trip_member`, seeding the
  five fixture users and the sample trip with its four members.
- `POST /api/trips` — create a trip for the caller.
- `GET /api/trips/{id}` — read one trip for a member.
- Backend validation for required name and destination, date order and malformed
  dates. Start and end locations are optional; absent, null or blank values are
  normalized to null, while supplied nonblank values are preserved.
- Create page and details page in the React app, including the required error,
  loading and denied states.
- Backend acceptance tests and the verification documents for the new endpoints.

## Out of scope

- Real authentication or authorization: no passwords, sessions, OAuth, tokens, or
  user administration. `X-User-Id` is trusted as given.
- Invitations and joining (US-008/US-010), member listing or management (US-013),
  trip editing or deletion, and the trip dashboard (US-061).
- Trip lists, search, sorting and pagination. A trip can only be opened by id.
- Notifications, i18n, ORM (JdbcTemplate stays), and any change to the CI job
  structure.
- Migrating or preserving data from the `greeting` capability.

## Scenarios and AC hints

| id | Scenario | Observable outcome |
|---|---|---|
| C1 | Alice (`X-User-Id: 1`) creates "Singapore Friends Day", Singapore, 2026-12-05 to 2026-12-05, City Hall MRT → Merlion Park | `201` with the created trip; a stored row holds all six values, `organizer_id = 1`, and a `trip_member` row for user 1 exists |
| C2 | Alice submits start 2026-12-06 and end 2026-12-05 | `400` with `code = INVALID_DATE_RANGE`; trip row count is unchanged |
| C3 | Alice submits a blank or whitespace-only name | `400` with `code = NAME_REQUIRED`; trip row count is unchanged |
| C6 | Alice omits destination, sends null, or sends an empty/whitespace-only destination | `400` with `code = DESTINATION_REQUIRED`; trip and membership row counts are unchanged |
| C7 | Alice supplies a destination but omits either or both locations, or sends null/blank locations | `201`; unspecified locations are stored and returned as null; supplied nonblank locations are preserved; completion occurs only during later main-plan generation under OQ-6 |
| R1 | Ben (`X-User-Id: 2`) opens the details of "Singapore Friends Day" | `200` carrying Singapore Friends Day, Singapore, 2026-12-05, 2026-12-05, City Hall MRT, Merlion Park |
| R2 | Eve (`X-User-Id: 5`), not a member, requests the same trip | `403` with `code = NOT_A_MEMBER`; the body contains no trip field values |
| R2-N | Same request with no `X-User-Id` header | `401` with `code = USER_REQUIRED`; no trip data returned |
| R3-N | A member requests an id that does not exist | `404` with `code = TRIP_NOT_FOUND` |
| C4-N | Create with a malformed date (for example `2026-13-01`) | `400` with `code = INVALID_DATE`; nothing stored |
| C5-N | Create with an `X-User-Id` that is not a seeded user | `401` with `code = USER_REQUIRED`; nothing stored |

Every error response carries a stable machine-readable `code` so C2, C3, R2 and
the reverse cases are distinguishable while all of them are HTTP 400/401/403/404.
Human-readable messages are implementation text and are not part of the contract.

Two scenarios touch the same aggregate on purpose: C1 proves the write and the
membership side effect, R1 proves the read returns the same values.

## Constraints

- React frontend, Spring Boot / Java backend, embedded SQLite, Flyway — unchanged
  from the REQ-001 stack (`TODO.md`).
- No ORM; `JdbcTemplate` (REQ-001 non-goal).
- Dates are exchanged as ISO-8601 `YYYY-MM-DD` strings; the timezone in the test
  context (Asia/Singapore) does not affect a date-only value.
- Repository documentation in English (`AGENTS.md`).
- The two-job CI workflow is reused unchanged.

## Affected capabilities

New capability `trips` with three ADDED requirements:

- **Trip caller identity** — the `X-User-Id` contract shared by both endpoints,
  including the two rejection cases.
- **Trip creation** — `POST /api/trips`, its validation and its membership effect.
- **Trip detail read** — `GET /api/trips/{id}` and its membership authorization.

The `greeting` capability is untouched.
