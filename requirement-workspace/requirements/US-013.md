## Intent

Give every trip member one honest roster: who joined, and which row is the
organizer. The roster is a read-only projection of existing membership; it
does not expose personal preferences, readiness or planning state, and it is
closed to outsiders.

## Actors and boundaries

- Read permission: any member of the trip. The organizer is a member and uses
  the same endpoint; `organizer` is an identification flag, not a permission.
- Identity is the authenticated account/session principal established by the
  merged US-066 login flow; no session → `401 USER_REQUIRED`. The retired
  `X-User-Id` header does not authenticate trip endpoints.
- Denial order: authentication → trip existence → membership (matching
  `TripController.read`). An outsider learns nothing about the roster.
- Backend owns the projection and the access decision; the frontend never reads
  the database directly.
- The frontend owns Screen 7 rendering and the four mandatory states (loading,
  empty, error, permission denied) plus a no-trip guidance state.

## In scope

- `GET /api/trips/{id}/members`, member-only, read-only.
- Response `{tripId, members:[{userId, displayName, organizer}]}` ordered by
  ascending `userId`; each member appears exactly once.
- Organizer identification by comparing the row's `userId` with
  `trip.organizer_id`.
- Existing error vocabulary: `USER_REQUIRED` 401, `NOT_A_MEMBER` 403,
  `TRIP_NOT_FOUND` 404; denial bodies carry no member identities.
- Screen 7 inside the app shell at `#/members`: member rows with avatar
  initial, display name, organizer badge and member count; loading, empty,
  error, permission-denied and no-trip states.
- MODIFIED `app-shell` requirement: 成员 renders the real list and 分队 renders
  main's shipped split entry; neither tab is a not-implemented placeholder.
- Acceptance fixtures §US-013 and a read-only ATDD matrix.

## Out of scope

- Readiness, preference summaries, budgets and the readiness ring (US-026 /
  US-027 / US-031); the screenshot shows them but the issue's design scope
  excludes them.
- Generating the main plan, inviting more members, removing members, changing
  roles, transferring organizer, member profiles/accounts.
- Changing the merged authentication/session flow (US-066); US-013 consumes the
  authenticated principal. Split endpoints retain their separate
  `MEMBER_REQUIRED` anonymous code (accepted divergence, follow-up F2).
- List-all-trips, search, sorting, pagination or a new database table/column.
- Avatar image uploads; avatar treatment is a local visual choice.
- Changing the split, main-itinerary or invitation behavior.

## Scenarios and AC hints

| id | Scenario | Observable outcome |
|---|---|---|
| S1 | Ben (authenticated user 2) opens the member list of "Singapore Friends Day" | `200`; `tripId` is the trip's id; exactly four members with `userId` 1, 2, 3, 4; `organizer = true` only for Alice |
| S2 | Alice (authenticated user 1), the organizer, opens the same list | `200`; same four rows; Alice is still the only `organizer = true` row |
| S3 | Eve (authenticated user 5) requests the same list | `403`, `code = NOT_A_MEMBER`; the body contains no `userId`, `displayName` or organizer value |
| S4-N | A request carries no authenticated session | `401`, `code = USER_REQUIRED`; no member data |
| S5-N | A request carries only a retired `X-User-Id` header (blank, non-numeric or seeded id) | `401`, `code = USER_REQUIRED`; the header does not authenticate |
| S6-N | An authenticated member requests a trip id that does not exist | `404`, `code = TRIP_NOT_FOUND` |
| S7-N | Eve requests a trip id that does not exist | `404`, `code = TRIP_NOT_FOUND` (trip existence is checked before membership) |
| S8 | Eve is recorded as a member (invitation accept or documented test-only insert) and then reads the list | `200`; Eve appears exactly once; Alice is still the only organizer |
| S9 | A member reads the list after repeated membership inserts by the same user | The user still appears exactly once (`trip_member` composite primary key) |
| S10 | A member reads the list | The body contains no readiness, preference, budget or main-plan field values |
| U1 | The members screen loads for a signed-in member | A visible member list with the organizer badge; no readiness pills, preference summaries or generate action |
| U2 | The signed-in account changes from Ben to Eve (logout/login) while the members screen is open | The screen shows the permission-denied state and no member names; signing back in as Ben restores the list |
| U3 | No trip has been opened in the session | A guidance state links back to 行程; no fabricated members are shown |

Every scenario has an observable outcome. The reverse cases (S3–S7, S10, U2)
exercise boundary and denial behavior; U3 covers the empty-selection boundary.

## Constraints

- SQLite, `JdbcClient`/`JdbcTemplate`, no ORM; read-only query.
- `maximum-pool-size=1` and no `SELECT ... FOR UPDATE`; this change performs no
  write, so no concurrency control is needed.
- Frontend follows the merged shell/auth conventions and the shared `api()`
  helper (session cookies + CSRF); no new dependency. The design-system
  migration remains a separate track.
- Contractual values: path, status codes and error `code`s. Human-readable
  messages and visual wording are implementation text.

## Affected capabilities

- `trips` — **ADDED** requirement "Trip member list read". Existing identity,
  creation, detail-read and main-plan-state requirements are unchanged.
- `app-shell` — **MODIFIED** requirement "Placeholder tabs": 成员 tab content
  becomes the member list; 分队 renders main's shipped split entry; neither tab
  is a not-implemented placeholder; frame, dock order, active-tab rule and
  signed-in account bar unchanged.
- `invitations` — composed, not modified: accepted members appear in the list.
- `main-itinerary` — untouched: readiness/preference fields are not exposed
  here.
