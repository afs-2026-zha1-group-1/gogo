## Intent

Add the main-itinerary capability as one vertical slice: readiness-gated generation of a timed draft (fake provider as MVP production), review with validation status, and organizer confirmation that freezes the shared version and closes joining.

## Actors and boundaries

- Organizer-only writes (generate, confirm): non-organizer member → 403 `NOT_ORGANIZER` (I3 precedent); non-member → 403 `NOT_A_MEMBER`; missing identity → 401 `USER_REQUIRED`; unknown trip → 404 `TRIP_NOT_FOUND` (fixtures codes; only `code` contractual).
- Members read the draft/confirmed plan; readiness and preference revision are inputs owned by the US-031-037 minimal read model (seeded; readiness flip test-only).
- Frontend owns Screen 9/10 rendering incl. required error/empty/loading/permission states; never reads the database directly.

## In scope

- US-031: readiness gate (all members ready at a preference revision), generation via `MainPlanProvider` port (fake = MVP production), draft persistence with ordered stops, activity times, travel legs, input revisions, per-person cost; draft NOT auto-confirmed; regeneration creates a new draft version; start/end location completion per signed 2026-11-14 ruling (preferences first, random fallback, supplied preserved).
- US-037: confirmation of the current draft only after schedule + hard-constraint validation (rule set per OQ-6 ruling); hard-budget overrun blocks with the overrun amount shown; on success the draft's version becomes the shared confirmed plan and joining closes (`main_plan_confirmed`, J4 behavior).
- Minimal self-contained schema on this branch (Flyway from V2): trip, member, readiness + preference snapshot, main-plan draft/confirmed with versions; seed users/trip per fixtures.
- Frontend Screen 9 (generate inputs/rules summary) and Screen 10 (draft timeline, validation status, blocked confirmation with errors, confirmed state) with the four required states.

## Out of scope

- Preference-entry UI (US-019~027) — later REQ; snapshots are seeded/test-set here.
- Split/group-assignment flows — later REQs; "confirmed v1" is their premise, not this deliverable.
- Real provider integration (port seam only), session auth, notifications (email/push), soft-budget enforcement (AC names hard budget only; OQ-10 ruled 2026-11-15: NULL hard budget = no limit, soft budget recorded as follow-up), invitation behavior changes (REQ-004 already specifies closed-joining; this REQ only sets the flag).
