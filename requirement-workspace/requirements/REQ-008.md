## Intent

Replace the scaffold identity with a real account boundary. A traveler proves
who they are once on a login page; from then on the browser carries a session
cookie and the backend derives the caller from that session. A guest who opens
an invitation keeps the public preview they already have, is asked to log in
only when they act, and comes back to the same preview before explicitly
accepting. Nothing about trip creation, membership rules or invitation outcomes
changes; only how the caller is identified.

## Actors and boundaries

- **Authenticated account:** a row in `app_user` with matching credentials.
  Membership and organizer rights stay exactly as defined by `trips` and
  `invitations`; authentication proves identity, it does not grant membership.
- **Session:** server-side state held by Spring Security, referenced by an
  HttpOnly session cookie. The session, not a request header, is the only source
  of the caller id for protected endpoints.
- **Public surfaces:** the login page and its endpoints, `GET /api/greeting`,
  and `GET /api/invitations/{token}` (preview). Invitation preview must stay
  identity-free and must not reveal member, itinerary or preference data.
- **Protected surfaces:** everything else in the trip domain, including
  `#/` (仪表盘/dashboard), `#/trips/<id>`, `#/create`, `#/members`, `#/split`,
  the split-draft flow, main-plan screens, `POST /api/trips`,
  `GET /api/trips/{id}`, invitation issuance and acceptance, and future trip
  features. The guest join page `#/join/<token>` is public to view; its accept
  action requires a session.

## In scope

- New `account_credential` table (one row per account) with a unique email and a
  BCrypt password hash, seeded for the five fixture users by Flyway `V6`
  (V1–V5 are occupied: V4 = splits, V5 = main plan); no registration, password
  change or reset.
- A JSON login endpoint accepting email + password, returning the authenticated
  account (id, display name, email) and establishing a server-side session;
  generic failure for unknown email and wrong password alike.
- A current-session endpoint returning the authenticated account, and a CSRF
  token bootstrap for the SPA.
- Spring Security configuration: BCrypt password encoder, session fixation
  protection, configurable session timeout, JSON 401 for unauthenticated API
  requests, CSRF protection on state-changing requests, and no accidental
  form-login or logout surface (logout belongs to US-069).
- Replacing the `X-User-Id` header with the session principal in the trip,
  invitation and main-plan packages, and in the merged `splits` package
  (`hello/splits`, five split-draft endpoints); the splits `MEMBER_REQUIRED`
  outcome and `{data,error}` envelope are kept as an explicit exception.
- Flat `{code,message}` errors for auth, trip, invitation, main-plan and the
  Security entry point/denied handler; no third error shape. A request with
  only the old header is unauthenticated.
- Frontend auth bootstrap, a dedicated full-screen login page, a route guard
  for protected pages, removal of the identity switcher and seeded-user list,
  and automatic resume of a pending invitation preview after login; the merged
  split feature's identity bar and split API client move to the session.
- Updating fixtures, backend acceptance tests (trip, invitation, main-plan and
  splits suites) and browser verification to log in instead of sending the
  header.
- Living-spec deltas: new `auth` capability; MODIFIED caller-identity
  requirements in `trips`, `invitations`, `main-itinerary` and `splits`;
  MODIFIED shell identity/login surface in `app-shell`.

## Out of scope

- Logout and session invalidation UI (US-069); My Account, email display and
  display-name editing (US-068); registration, password reset/change, email
  verification, SSO, social login, remember-me and multi-device session
  management.
- Invitation QR scanning (US-067); dashboard aggregation (US-061); new split
  behavior beyond the identity migration; member-management writes; roles and
  permissions beyond the existing membership rules.
- Production secret management, HTTPS termination, rate limiting and account
  lockout (deployment concerns, not this story's AC).
- Changes to trip creation, details, invitation outcomes, join rules or shell
  frame/dock behavior beyond identity and login placement.

## Scenarios and AC hints

| id | Scenario | Observable outcome |
|---|---|---|
| S1 | A signed-out traveler with no pending invitation submits a valid seeded email + password | Login returns 200 with the account; a session cookie is set; `GET /api/auth/me` returns the same account; the dashboard (`#/`) opens and the dock is visible |
| S2 | A signed-out traveler opens `#/join/<token>` (preview), then logs in | The preview is public before login; after login the same invitation preview resumes with the token; no membership row is created until the traveler explicitly accepts |
| S3 | Login is attempted with an unknown email or a wrong password | The response is 401 with one generic credential error; no session is created; neither the existence of the email nor any account or trip data is revealed |
| S4 | A signed-out traveler opens `#/trips/<id>` or `#/create`, or calls a protected endpoint directly | The page opens the login page; the direct request returns 401 with `code = USER_REQUIRED`; no trip, member, invitation or account data is returned |
| S5 | A session expires, then a protected page or endpoint is used | The endpoint returns 401 `USER_REQUIRED`; the page opens the login page; no private data is shown; logging in again restores access |
| S6 | Alice logs in and creates a trip; Ben logs in and reads it; Eve logs in and reads it; Alice issues an invitation; Eve accepts it | Create records Alice as organizer; Ben reads 200; Eve reads 403 `NOT_A_MEMBER`; only Alice can issue; Eve's accept creates one membership and her next read is 200 — all with the same rules as before |
| S7 | `GET /api/greeting` and `GET /api/invitations/{token}` are called without a session | Both remain available; the preview carries only the public trip basics and no member/itinerary/preference data |
| S8 | A state-changing request is sent without a valid CSRF token, then with one | Without the token the request is rejected and changes nothing; with the token it behaves as in S1/S6 |
| S9 | A request carries only the old `X-User-Id` header and no session | It is treated as unauthenticated (401 `USER_REQUIRED`); the header no longer grants access |
| S10 | Login succeeds on an existing anonymous session | The session id changes (fixation protection) and the old session identifier no longer authenticates |
| S11 | Re-run existing acceptance behavior for create validation, details permission, invitation panel and join flow while logged in | Outcomes and error codes are exactly as today; only the identity source changed |

Reverse cases for non-goals: no header fallback in production (R-1); no logout,
account-edit or registration endpoint/UI (R-2); no identity switcher or seeded
user list in the frontend (R-3); no private data in login errors or public
preview (R-4); no plaintext password storage or logging (R-5); no change to
membership or joining rules (R-6).

## Constraints

- Spring Boot 3.5 + `JdbcTemplate` + SQLite + Flyway, React + Vite, hash router.
  The binding `docs/knowledge/architecture/tech-stack-plan.md` does not define an
  authentication stack (it says the MVP has no accounts), so this change
  **deliberately deviates** by adding `spring-boot-starter-security` and a
  credential table; the conflict is recorded in the proposal and reconciled at
  archive per `openspec/config.yaml`.
- Session storage is the application server's HTTP session (single instance);
  credentials are persisted in SQLite. No external identity provider or
  service.
- BCrypt is the password hash; passwords are never stored or logged in plaintext
  and are never returned by any endpoint.
- CSRF protection is mandatory for state-changing requests; the SPA obtains the
  token from the backend and sends it in the expected header.
- Login page is full-screen without the dock; shell pages shown after login keep
  the existing frame and dock. The identity switcher and fake user list are
  removed; no replacement "switch user" affordance exists.
- UI uses the repository's Ant Design reference and existing tokens; adding a UI
  component library is not required by any AC.
- Depends on REQ-003/REQ-004/REQ-005 code being present (it is, on main); no
  dependency on US-061/US-067/US-068/US-069.

## Affected capabilities

- **New `auth` capability:** credential storage and password verification; login
  and session establishment; current-session read; CSRF bootstrap; protected
  request enforcement; login page and post-login resume behavior.
- **`trips` (MODIFIED):** caller identity requirement moves from `X-User-Id` to
  the authenticated session; creation/detail behavior and error codes stay.
- **`invitations` (MODIFIED):** issuance and acceptance move to the session
  principal; preview stays public and identity-free; identity-error precedence
  stays.
- **`app-shell` (MODIFIED):** identity switcher removed; login page is
  full-screen without the dock; shell pages render only for signed-in travelers;
  join preview stays outside the dock.
- **`greeting`:** unchanged and public.
- **`main-itinerary` (MODIFIED):** its identity requirement moves to the
  session principal with the same organizer/member outcomes and codes.
- **`splits` (MODIFIED):** the five split-draft endpoints move to the session
  principal; `401 MEMBER_REQUIRED` and the `{data,error}` envelope remain the
  documented exceptions. No split behavior changes.
