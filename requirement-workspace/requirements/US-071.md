## Intent

给每个已登录旅行者一个「我的行程」列表：打开底部「行程」tab 就能看到自己创建和加入的全部行程，点一下进入详情。列表是既有归属关系的只读投影，只对当前会话账号可见，不暴露任何他人行程，也不伪造演示数据。

## Actors and boundaries

- 读取范围：当前会话账号在 `trip_member` 中的全部行程（含自己创建的，创建时会写入 organizer 成员行）。
- 身份：US-066 会话主体；无会话 → `401 USER_REQUIRED`；退役的 `X-User-Id` 不再认证。
- 后端拥有范围查询与字段投影，不做「已结束」状态机（只返回 `endDate`）。
- 前端拥有列表页渲染、已结束标记判定（`endDate` < 本地当天）与四个状态（loading / empty / error+重试 / 列表）。
- 「行程」tab 恒指向 `#/trips`；`main-plan` 等深链仍可通过详情页进入，不由 tab 直达。

## In scope

- 新增 `GET /api/trips`：返回当前会话账号作为成员的行程包封套 `{trips:[...]}`；每项 `{id, name, destination, startDate, endDate, organizer, mainPlanConfirmed}`；按 `start_date` 升序、同日按 `id` 升序；每个行程恰好一条。
- `organizer` = 该行程 `organizer_id` 等于当前账号（布尔），用于行内标识，不代表额外权限。
- 行程列表页（`#/trips`）：列表项显示名称、目的地、`startDate – endDate`；自己创建的行程追加「我创建的」徽标（`organizer=true`）；点击进入既有 `#/trips/{id}` 详情。
- 已结束标记：`endDate` 早于当天 → 行内显示「已结束」徽标；仍在同一列表，不分区、不隐藏。
- 空列表：文本空态 + 「创建行程」入口（跳 `#/create`）。
- loading 态；加载失败 → 错误信息 + 重试按钮（重试重新请求列表）。
- 账号切换/刷新后重新读取：只显示当前账号的行程。
- 行程详情页（`#/trips/{id}`）的「主线方案」入口：**已由 US-072（2026-11-16 归档）交付**，本故事不重复实现，只做回归验收（tab 改为列表后 `#/trips/{id}/main-plan` 仍可达）。
- 行程内返回链接：成员名册「返回行程」保持指向 `#/trips/{id}`；分队无行程时的「去行程」与创建页返回指向 `#/trips`（`tripsHref` 不再单一复用）。

## Out of scope

- 分页、搜索、筛选、排序切换（MVP 行程量小，记 OQ-5 `deferred`）。
- 行程删除/归档/退出、角色变更、成员管理。
- US-061 的单行程仪表盘语义、main-plan 生成与确认逻辑。
- 邀请、成员名单、偏好、预算、分队等任何既有能力的读取或写入变更。
- 新表、Flyway 迁移、数据回填、缓存层。
- 「按编号打开行程」入口（用户裁决移除）；`#/trips/{id}` 深链本身保留。
- logout / 切换账号的 UI（US-069 / issue #41 已覆盖，本故事只在 API 层验收跨账号隔离，见 OQ-9）。

反向 / 边界：

- R1：无会话请求 `GET /api/trips` → `401 USER_REQUIRED`。
- R2：仅携带退役 `X-User-Id`（含合法种子 id）→ `401 USER_REQUIRED`。
- R3：列表永不包含请求者不是成员的行程，也不返回这些行程的名称/目的地/日期。
- R4：同一行程只出现一次（`trip_member` 复合主键保证归属唯一；投影不做笛卡尔展开）。
- R5：空列表返回空数组，前端显示空态，不注入演示行程。
- R6：`GET /api/trips` 只读；对集合路径的 POST/PUT/DELETE 不新增（POST 仍为创建）。

## Constraints

- 身份：US-066 会话；`/api/**` 已由 `SecurityConfig` 要求 `authenticated()`，新增 GET 自动受保护，**不需要**新增 permitAll 匹配器。
- 数据：仅读 `trip` + `trip_member`（V2）；`main_plan_confirmed` 列已存在；**零迁移**。
- 响应风格：包封套（用户裁决 2026-11-16），与既有 `{tripId, members}` 一致。
- 排序契约：`start_date` 升序 → `id` 升序（可确定性断言）。
- 「已结束」判定在前端（客户端本地日期 vs `endDate` 字符串 `YYYY-MM-DD`）；服务端不引入状态字段。已结束**仅表达展示语义**，不改变邀请加入（只由 `mainPlanConfirmed` 控制 `JOINING_CLOSED`）、主线方案生成/确认、分队等任何写能力。
- 排序后果已知：`start_date` 升序会让已结束的旧行程排在首屏，本期按用户裁决接受；若后续需「未结束优先」另立变更。
- 前端：shadcn/ui 组件 + `frontend/src/index.css` 的 `@theme` tokens；沿用现有 hash 路由与 `api()` 请求层；列表数据用**手写 `api()` + `useEffect`**（不引入 TanStack Query）；不引入第二 UI 库。
- 语言与文案：界面中文；错误信息沿用 `code: message` 既有格式。

## Context

- 现状：`#/trips` 渲染 `TripsEmpty`（标题「还没有打开的行程」，含「按编号打开行程」输入）；`App.tsx` 中 `tripsHref = lastTripId != null ? #/trips/{id}/main-plan : #/trips`，被 TabBar 的「行程」tab、分队未选行程、成员页、创建页返回共用。
- 后端 `TripController` 仅有 create / read / members / confirm 四个入口；`TripRepository` 无按用户列行程的查询。
- Living Spec 冲突点：`app-shell` 的「Trips tab placement and no-trip empty state」明确禁止列表端点与调用，且要求空态提供「创建行程 + 按编号打开行程」两个动作 → 本变更以 MODIFIED 收敛。
- 被取代的验收基线：REQ-005（US-064）的 `docs/feedback/verification-req-005.md` TR2（空态两动作）、TR3（编号输入校验）、TR4（create 返回 `#/trips/1`）、TR5（无 `GET /api/trips`）在本变更合并后不再成立，旧记录仅作历史证据。
- 相邻故事：US-072（2026-11-16 归档，G1/G2/G3 Pass）已在 `TripDetails.tsx` 交付「主线方案」入口，Living `trips` 已有 requirement「Trip detail main-plan navigation entry」；本变更不再拥有该行为。

- 与 US-061 的区别：本故事只做「列表 + 进入详情」，不做单行程仪表盘聚合。

## Affected capabilities

- `trips`：ADDED「Trip list read」（`GET /api/trips`，成员范围、包封套、排序契约）；行程详情页主线入口归 US-072，本变更仅回归。

## Revision（2026-11-17，用户指令：当前行程模型）

P4 完成后用户提出范围修订，**取代**本条目原「行程 tab = 列表」的语义：

1. 「我的」页（`#/account`）新增入口，标题「我的行程」，进入新页面 `#/my-trips`。
2. `#/my-trips` 展示原 `#/trips` 的列表数据（成员范围、双徽标、四态不变）；**点列表行 = 设为当前行程并立即跳「行程」tab**。
3. 「行程」tab（`#/trips`）展示**当前行程的详情**（即原 `#/trips/<id>` 详情页内容）；未选过当前行程时显示空态 + 「去我的行程选择」引导。
4. 「当前行程」**后端持久化**（每用户一个），跨刷新/跨设备一致。
