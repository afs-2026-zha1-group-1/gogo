# US-093 — 从多条初始路线继续拆分分支并会合

- 覆盖：US-093（草稿故事；GitHub issue 尚未关联）
- 依赖：US-038/039/042/043（发起草稿、边界、路线生成与时间校验）、US-049/050（确认、取消）、US-086（队伍路线图）
- Discovery Decision：**Draft** — 初始分队支持生成两条或三条路线；既有路线可再拆为两个子路线（首个示例为 Route B → B1 / B2），各路线最终重新会合
- 原型参考：[多路线分支截图](../../ui-design-reference/screenshots/us-093-branching-routes.png)；[可打开的 mock 页面](../../ui-design-reference/us-093-branching-routes-mock.html)

## 意图

允许组织者在首次分队时直接生成两条或三条并行路线，并可从一条已有路线（例如 Route B）继续拆出两个子路线（B1 / B2）。子路线先回到其父路线，再与其他路线在共同会合点汇合并继续全员主线。路线树和各级分头/会合点均属于同一份草稿，避免把嵌套分支误表示成彼此无关的顺序分队轮次。

## 范围与边界

- 前端：需要；后端：需要；数据库：预期需要以可持久化且可原子确认的形式保存路线树，具体数据模型与迁移在技术设计阶段决定。
- 首次分队允许选择生成两条或三条路线；MVP 至少支持从其中一条路线再拆出两个子路线。是否支持更深层或更多子分支由技术设计确定。
- 父路线拆出的子路线成员只能来自该父路线的成员；不同父路线及子路线在各自层级保持明确、互斥的成员归属，并在父会合点恢复父路线成员集合。
- 所有路线段复用现有时间可行性及成员访问规则；整份路线树仍由现有组织者确认、发起人取消的权限约定控制。
- 修改或重新生成某个父路线节点/边界时，所有依赖该节点或边界的子路线必须标记为需要重新校验或生成；精确失效范围由技术设计定义，未定义前不得假设依赖路线仍有效。
- 既有单轮记录必须继续按原单轮路线读取；新增路线树数据模型的向后兼容方案由技术设计确定。
- 不包括真实地图供给、自动路线优化、成员通知、节点任务完成写入或跨多天分队。

## 验收标准

1. 给定主线方案已确认且行程成员满足现有分队前置条件，当组织者选择首次分队路线数时，那么可以选择生成两条路线或直接生成 Route A、Route B、Route C 三条路线；三条路线从同一主线分头并在共同会合点汇合。
2. 给定 Route A、Route B、Route C 已生成，当组织者对 Route B 选择「再拆分」时，那么 Route B 可拆为 Route B1 与 Route B2；Route A 和 Route C 保持原路线，B1/B2 在父路线指定的会合点重新汇入 Route B。
3. 给定路线树包含初始分支和 Route B 的子分支，当成员查看完整路线时，那么图中能清晰区分共同主线、Route A/B/C、Route B 的二级分支 B1/B2、父会合点与全员会合点，并按时间顺序呈现分头、活动、子会合及最终会合。
4. 给定组织者设置任一分头或会合边界时，那么每个分头点必须位于其父路线有效区间内，子路线的会合点必须晚于该子分头点，父路线的后续节点必须晚于子会合点，最终各顶层路线须在共同会合点汇合；无效边界被拒绝并指出对应路线，不改变已保存的有效草稿。
5. 给定任一路线或子路线正在生成或校验，当路线生成失败、缺少必需时长或超出其可用会合窗口时，那么系统指出具体路线并阻止整份路线树确认；不得把其他路线通过校验误显示为整份方案有效。
6. 给定组织者修改某一路线的边界或生成输入，当修改保存时，那么该路线及依赖它的所有子路线标记为过期并需重新校验/生成；不依赖该路线的分支保持可查看，最终确认仍要求路线树中所有路线均有效。
7. 给定路线树中所有顶层路线、子路线及会合节点均完整且校验通过，当组织者确认分队方案时，那么服务端按既有确认权限与校验规则一次性确认整份路线树；不得只确认部分分支。确认后所有路线及边界锁定，成员看到同一份已确认方案。
8. 给定组织者取消尚未确认的多路线草稿，当取消成功时，那么整份路线树一并失效，原主线不变；不得只取消或遗留部分子路线。给定旧行程只有一个 A/B 分队，当其读取或确认时，现有单轮路线继续按原有方式显示和工作。
9. 给定我是非成员或未登录用户，当我请求包含多路线或嵌套分支的私人路线或草稿时，那么访问按现有身份与成员权限规则拒绝，不泄露路线、成员分组或边界信息。
