## Intent

Give an invited traveler a camera-based way to join a trip: point the phone at
a friend's QR code, have the app recognize the gogo invitation URL, and
hand off to the existing preview-and-accept flow. The scanner must be respectful
of the camera (lazy start, release on leave) and forgiving of failures (retry,
manual link fallback). Scanning alone must never create a membership — the
explicit accept step (US-010) remains the gate.

## Actors and boundaries

Same identity model as REQ-003/004: `X-User-Id` header, seeded users, no real
authentication. The scanner is a **frontend-only** surface. It owns:

- Camera lifecycle (`navigator.mediaDevices.getUserMedia`, stop tracks on close)
- QR frame decoding (browser `BarcodeDetector` API or `jsqr` library)
- URL pattern validation: decoded text must match the invitation link pattern
  (`<origin>/#/join/<token>`, token in the hash fragment) to be treated as a
  gogo invitation
- Fallback invitation-link text input

The scanner does **not** own:

- Invitation preview rendering or accept logic (delegated to existing Join page / US-010 flow)
- Membership creation, duplicate protection, joining-closed gate (backend, REQ-004)
- Navigation entry point (scan icon placement — deferred, see OQ-3)

## In scope

- Scanner screen UI per the design basis (Ant Design interaction patterns plus
  the existing `app.css` tokens): app bar titled 扫码加入行程 with a close
  control, camera preview area, 开始扫描 primary action, 从相册选择 secondary
  action, invitation-link input with a 预览邀请 action.
- Camera permission requested only when the user explicitly taps "Start camera".
- Camera stream released when the user closes or navigates away from the scanner.
- Closing the scanner returns to the route it was opened from, falling back to
  `#/` when no in-app history exists.
- QR decode of a live camera frame or a chosen image file.
- URL validation: decoded text must carry the complete hash form
  `#/join/<token>` with a 32-character lowercase hexadecimal token; an absolute
  URL is accepted only when its origin equals the current app origin. A
  recognized token is extracted and routed to the existing Join page
  (`#/join/<token>`) which renders the US-010 preview-and-accept flow.
- Non-matching, malformed-token, or cross-origin QR content → show
  "unrecognized code" feedback; do not navigate.
- Error states: camera permission denied, camera hardware unavailable, QR
  unreadable → recoverable panel with retry action and the invitation-link
  text-input fallback.
- Invalid / revoked / closed invitation tokens encountered after handoff to
  the Join page follow existing REQ-004 rules (U1/U2, J4); no new backend
  behavior.
- Already-member duplicate protection follows existing J3/J6 behavior.

## Out of scope

- Scan icon placement beside the "i" control on the dashboard (AC scenarios 1–2;
  deferred per OQ-3 to a later UI integration story).
- Navigation trigger / routing entry point to open the scanner (deferred with
  scenario 1–2).
- Login / authentication flow itself (owned by the in-flight US-066 change; AC
  scenario 9 signed-out → login → resume is not exercised in this REQ, the
  scanner only hands off to `#/join/<token>`).
- New backend endpoints, Flyway migrations, or data model changes.
- Invitation issuance (US-008), revocation, expiry.
- Push notifications or deep-link handling outside the app.

Reverse / boundary cases:
- R-1: Scanning a valid QR must NOT call `POST /api/invitations/{token}/accept`
  automatically; acceptance requires explicit user action on the Join page.
- R-2: An unrelated QR (e.g. a URL to `https://evil.example.com`) must NOT
  cause any navigation or API call.
- R-3: Closing the scanner must stop all camera tracks even if the user
  navigates away via browser back.

## Constraints

- React / TypeScript frontend, Vite dev server — existing stack.
- Browser APIs: `navigator.mediaDevices.getUserMedia` for camera;
  `BarcodeDetector` (where available) or `jsqr` for frame decoding. Fallback:
  manual invitation-link text input.
- No new backend code, no Flyway migration.
- URL validation: decoded text must carry the complete hash form
  `#/join/<token>` where the token is 32 lowercase hexadecimal characters; an
  absolute URL is accepted only when its origin equals the current app origin,
  a relative or hash-only form is always accepted, and any other origin is
  rejected as unrelated.
- UI basis: Ant Design mobile interaction patterns + the existing `app.css`
  tokens; no scanner screen exists in `ui-design-reference/`, so the delta-spec
  layout is the reference and no prototype screenshot is cited.
- Accessible name "Scan invitation" on the scanner entry (when entry point is
  eventually built; not exercised in this REQ's tests).
- Repository documentation in English (`AGENTS.md`).

## Affected capabilities

- `invitations`: one ADDED requirement "QR-code invitation scanner" (frontend
  scanner surface, camera lifecycle, URL validation, link fallback). No backend
  requirement changes.
- `app-shell`: one MODIFIED requirement "Mobile shell frame" — `#/scan` is a
  full-screen flow (no dock, scaffold bar retained, no dock tab, close returns
  to the originating route).
- `trips`, `greeting`, `main-itinerary`: untouched.
