# Intent — REQ-026 提交偏好并标记就绪（US-026 + US-027）

- Date: 2026-11-15
- Stories: US-026 "Submit My Preferences" + US-027 "Choose No Preference"（用户裁定合并为一个需求）
- Change: `openspec/changes/req-026-submit-preferences/`

## 为什么合并

两个故事的**动作**是同一个：成员把自己的偏好状态**提交**给团队。差别只在提交的**结果**：

- 结果 A（US-026）：带着已保存的兴趣 / 必做项 / 预算提交 → `ready`，输入供主线生成使用。
- 结果 B（US-027）：显式声明「我没有特别偏好」→ 也是 `ready`，但个人值不再参与生成，改用默认画像（步行 + 标准节奏）。

如果拆成两个变更，会出现同一张「提交状态」表被两个变更先后改写的堆叠，且「沉默≠同意」这条规则会被劈成两半。合并后只有一条状态机：`pending → ready(noPreference=false | true)`。

## 裁定（D1–D14）

- **D1 一变更两故事**：`req-026-submit-preferences` 覆盖 US-026 + US-027；状态机只有 `pending → ready`，`noPreference` 是 `ready` 的两种子态。
- **D2 存储**：复用 `member_preference`，`kind='submission'`，单行单对象 payload；**零迁移**。语义上它不再是「偏好内容」而是「提交状态」，与 `tech-stack-plan.md` §5 的四类枚举有意偏离（REQ-019 的 DoV 已裁定「`kind` 取值域由后续 story 扩展」）。
- **D3 端点**：`PUT /api/trips/{tripId}/preferences/submission`（写，幂等覆盖）+ `GET /api/trips/{tripId}/preferences/readiness`（全员就绪名册）+ `GET /api/trips/{tripId}/preferences/effective`（生成侧只读投影）。三个都是 `preferences` 能力的同级子资源。
- **D4 提交请求体**：`{"noPreference": false|true}`，键必须存在且必须是布尔；未知键忽略（不加 `additionalProperties:false`）。
- **D5 落库 payload**：
  - 有偏好提交：`{"status":"ready","noPreference":false,"submittedAt":"2026-11-15T10:12:00+08:00"}`
  - 无偏好提交：`{"status":"ready","noPreference":true,"submittedAt":"...","defaults":{"transport":"walking","pace":"standard"}}`
  - `submittedAt` 由服务端生成，Asia/Singapore 偏移的 ISO-8601；客户端不可写、不可改。
- **D6 pending = 没有 `submission` 行**。与预算「清除写 `{}` 保留行」不同：提交没有「空态」，这行一旦存在就意味着 ready。撤销提交（回到 pending）不在本需求范围。
- **D7 空提交判定**：`noPreference=false` 且该成员**四类偏好全无** → 400 `PREFERENCE_EMPTY`。「全无」的判定口径必须逐类写死：`interest` 无行或 `{"codes":[]}`；`must_do` 无行或 `{"items":[]}`；`budget` 无行或 payload 为 `{}`；`constraint` 无行（该 kind 尚未实现，判定必须容忍缺失）。
- **D8 默认画像**：`transport=walking`、`pace=standard` 固定写进 submission payload 的 `defaults`；无 UI 控件、不可配置；改变它需要新变更。
- **D9 投影语义**：`effective` 只列 ready 成员、按 `userId` 升序；pending 成员**不出现**（沉默≠同意）。`noPreference=true` 的成员个人值一律不出现（`interests:[]`、`mustDos:[]`、`budget:null`、`constraints:null`），只给 `defaults`。投影只读，不写库、不刷新任何时间戳。
- **D10 就绪不被后续保存撤销**：提交之后再保存兴趣/必做项/预算，`readiness` 仍为 ready、`submittedAt` 不变。
- **D11 名册**：`readiness` 返回**全员**（含 pending）+ `readyCount` / `memberCount` / `allReady`；`allReady` 只表示「全员已提交」，主线是否已确认、成员数下限等生成前置换 US-031 自行组合。
- **D12 校验顺序固定 8 步**：身份 → trip 存在 → 成员 → body 是对象 → `noPreference` 键存在 → 类型为布尔 → 空提交判定 → 写库；任一步失败零写入。
- **D13 幂等**：重复提交相同 body → 200，行数恒 1，`noPreference` 不变，`submittedAt` 刷新为本次提交时间（同 REQ-019 对 `updated_at` 的口径）。
- **D14 错误码**：新增 `PREFERENCE_EMPTY`(400)、`INTERNAL_ERROR`(500)；复用 `USER_REQUIRED`(401) / `NOT_A_MEMBER`(403) / `TRIP_NOT_FOUND`(404) / `INVALID_REQUEST`(400)；全部沿用 `{"code","message"}` 裸体。

## 已知偏离与待跟踪

1. **`kind` 取值域偏离**：计划 §5 只有四类偏好，`submission` 是第五个取值，且语义不是「偏好」。
2. **计划 §6 没有这三个端点**：计划写「`PUT /preferences` 一次提交四类偏好」；本需求把「提交」独立成子资源，与 REQ-019/020/024 的独立端点路线一致。
3. **参考图的 `submitPref()` 被重新定义**：原型里它同时保存四段字段并标记就绪；本需求里它只负责「提交就绪」，四段各自的保存时机不变（兴趣显式、必做项即时、预算段内显式）。这反而**修好了** REQ-024 记录的 R8 冲突点。
4. **参考图的 `noPrefSw` 只 `hide` 字段**：实现必须真的写服务端标记 + 让投影按 D9 生效。
5. **空提交拒绝是本需求新增的规则**：AC 未写，但它是「沉默≠同意」的必然推论，须在 G1 作为一条明确裁定复核。
6. **500 错误码 `INTERNAL_ERROR` 是新的**：既有 advice 没有 500 映射，AC2 需要可展示的错误体。
7. **`submittedAt` 与表内 `updated_at` 双份时间**：payload 里的 `submittedAt` 是读契约权威（带 +08:00 偏移，便于界面直显），`updated_at` 仍是既有 housekeeping 列（UTC），两者不要求相等——已在 deep-dive ⑨ 写明，避免 P4 拿 `updated_at` 当断言依据。
8. **REQ-020 文档里的错误码与代码不符**：`analysis/req-020-dor.md` 与 `req-020-manage-must-do/proposal.md` 写的是 `UNAUTHENTIC` / `TRIP_FORBIDDEN`，而 `TripController` 实际是 `USER_REQUIRED` / `NOT_A_MEMBER`。本需求按代码实况写，并把这处漂移登记为跨 REQ 一致性问题（待 REQ-020 的 P2 修订或 G1 条件处理）。
   - **P2 复核推翻（2026-11-15）**：REQ-020 的两份文档从未出现这两个码——`git log -S "UNAUTHENTIC"` 与 `-S "TRIP_FORBIDDEN"` 首次引入即本需求的 `16e201f`，REQ-020 的 `proposal.md:39` 写的是复用四个既有 code。OQ-10 以「前提不成立」关闭；「按代码实况写」的结论不变。
