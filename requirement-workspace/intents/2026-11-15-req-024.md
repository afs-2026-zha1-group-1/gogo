# 意向记录 — REQ-024（US-024 成员全程预算）

- 日期：2026-11-15
- 来源：US-024「Set My Trip Budget」（Category: Preferences；Priority: Must；Frontend/Backend/Database 三层）
- 变更包：`openspec/changes/req-024-set-trip-budget/`
- 变更序位：本人负责的第三个需求（第 1 = US-019 / REQ-019，第 2 = US-020 / REQ-020）

## 原始陈述

行程成员可以保存一个**可选**的、**非负**的、**人均全程**预算，并带上币种与「硬上限 / 软上限」标记，
使后续方案生成可以拿已知成本对照我的花费需求校验。

三条 AC：

1. 主线未确认时，Alice 保存 40 SGD 硬上限，随后改成软上限 → 金额与币种仍是 40 SGD，上限类型变为软。
2. Alice 提交 -1 SGD → 被拒，且她之前的预算保持不变。
3. Alice 留空预算，或保存 0 SGD 硬上限，提交合法偏好时两种输入都被接受，**未设置必须区别于 0**。

Design scope：可选金额、币种、硬/软选择器；**支持 SGD**；区分未设置与 0；参考图里的币种与金额只是示意。

## 澄清轮次

### 第一轮（4 项，全部 resolved）

| 议题 | 候选 | 用户裁定 |
|---|---|---|
| 存储归属 | 复用 `member_preference` kind='budget' / 新建 `member_budget` 表 / 拆多行 | **数据库设定以 `docs/knowledge/architecture/tech-stack-plan.md` 为准** → 该文档 §5 的 `kind` 枚举本就含 `budget`，且「一张表装四类偏好，避免四张宽表」→ 复用表、零迁移 |
| 端点与写入时机 | 独立端点 + 段内显式保存 / 动作即保存 / 并入 `PUT /preferences` | 独立端点 + 段内显式保存 |
| 币种与金额 | 白名单含 SGD + 整数 / 只支持 SGD / 任意三码 | 白名单含 SGD + 整数 |
| 读取范围 | 全员明细 + `budget:null` / 仅自己 / 全员但省略未设置者 | 全员明细 + `budget:null` |

### 第二轮（1 项，resolved）

| 议题 | 候选 | 用户裁定 |
|---|---|---|
| 金额单位 | 最小货币单位整数（40 SGD → 4000）/ 主单位整数（40）/ 存分且去掉 JPY | 最小货币单位整数 |

裁定依据：`tech-stack-plan.md` §5 写「金额用 `INTEGER` 分」，与未来 US-031 的 `attraction.price_cny` 必须可直接比较；
代价是 AC 的主单位读法要靠前端换算提供证据，且 JPY 无小数位需在契约里单列。

## 决策台账

| id | 决策 | 依据 |
|---|---|---|
| D1 | 独立变更 `req-024-set-trip-budget`，堆叠在 REQ-019 → REQ-020 之后 | 三需求共用 `preferences` 能力与同一页面，链式 MODIFIED 不能并行 |
| D2 | 复用 `member_preference`，新增 `kind='budget'` 的**单行单对象** payload；**零迁移** | `tech-stack-plan.md` §5（kind 枚举含 `budget`、一表装四类）+ 用户裁定 |
| D3 | 端点：`GET` / `PUT /api/trips/{tripId}/preferences/budget`（单数，1:1 资源） | 用户裁定；避免改 REQ-019 已冻结的 `/preferences` payload |
| D4 | 写入时机：预算段**显式保存**，一次提交 `amount` + `currency` + `limitType` | 用户裁定；AC3 的 "submits valid preferences" 措辞 |
| D5 | 币种白名单 `{SGD, CNY, USD, EUR, JPY}`，严格大写三码，不做大小写归一化 | 用户裁定；Design scope 的 "Support SGD" + 参考图的其它币种都不失效 |
| D6 | 金额为**最小货币单位**整数：`SGD/CNY/USD/EUR = 2` 位小数，`JPY = 0` 位；40 SGD → `4000` | 用户裁定；`tech-stack-plan.md` §5「金额用 INTEGER 分」 |
| D7 | 「未设置」= `amount:null` 且 `currency`、`limitType` 同为 null；GET 返回 `budget:null`；库里保留行、payload 为 `{}` | AC3「unset 必须区别于 0」；沿用 REQ-019/020 的「保留行」口径 |
| D8 | 联动必填：`amount` 非 null ⇒ `currency` 与 `limitType` 都必须有值；`amount` 为 null ⇒ 另两字段必须为 null | 半个预算（只有金额没有币种/软硬）没有可校验语义 |
| D9 | `amount` 负数、小数、超出 int32 一律 `400 BUDGET_AMOUNT_INVALID`；`limitType` 仅 `hard`/`soft`，小写 | AC2 的 -1 必须被拒且零写入 |
| D10 | GET 返回全员明细，按 `userId` 升序；未设置者 `budget:null` | 用户裁定；US-031 的「约束/预算过滤」与参考图节点 7 的成员摘要都需要 |
| D11 | 错误码：新增 `BUDGET_AMOUNT_INVALID`、`BUDGET_FIELDS_INCOMPLETE`、`BUDGET_CURRENCY_NOT_ALLOWED`、`BUDGET_LIMIT_TYPE_INVALID`；复用 `USER_REQUIRED`、`NOT_A_MEMBER`、`TRIP_NOT_FOUND`、`INVALID_REQUEST` | 与 REQ-019/020 的错误码风格一致（裸 `{"code","message"}`） |
| D12 | 校验顺序固定：identity → trip → membership → body 可解析 → `amount` 键存在 → 金额 → 字段联动 → 币种 → 上限类型 → 写入；任一失败**零写入** | 多字段同时非法时结果必须确定，否则断言会摇摆 |
| D13 | 主线确认后仍可保存预算，**不设锁定分支** | 沿用 REQ-019 的 D4：AC 的 "main plan is unconfirmed" 是测试前提，不是状态机 |
| D14 | 幂等：重复 PUT 完全相同的 body → 均 200，行数恒为 1、payload 不变（`updated_at` 可刷新） | AC1/AC2 的「不产生第二条」在预算场景等价于「行数恒 1 + payload 是单对象而非数组」 |

## 已知偏离

| 偏离 | 内容 | 处置 |
|---|---|---|
| 金额单位 | API/payload 用最小单位（40 SGD → 4000），AC 的「40 SGD」是界面读法 | 前端负责换算显示；P4 断言必须写明 `4000` 与界面 `SGD 40.00` 的对应 |
| `tech-stack-plan.md` §6 | 计划写「`PUT /preferences` 一次提交四类偏好」，本需求用独立子资源端点 | 跟随 AC 与既有 delta；文档漂移并入 REQ-019 OQ-16 的团队任务 |
| `tech-stack-plan.md` §5 | 计划字段为 `member_id`、普通索引；实现为 `user_id`、UNIQUE | REQ-019 已登记，本需求不重复登记 |
| 参考图币种 | 节点 8 下拉只有 CNY/USD/EUR/JPY，不含 AC 要求的 SGD | 白名单补齐 SGD；参考图的金额 1200 只是示意，不改 |
| 页面写入时机 | 同页三段三种时机：兴趣显式保存、必做项动作即保存、预算段内显式保存 | 页面 requirement 需第三次 MODIFIED，按段写明 |
