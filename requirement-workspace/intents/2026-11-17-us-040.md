## 原始验收条件（AC）

1. 给定有可供分队的共同路线，任何行程成员发起分队草稿时，系统允许该成员发起草稿并选择分队边界。
2. 给定分队处于草稿阶段，成员选择或更换自己的小组时，该成员仅属于所选小组，不能替其他成员选择；分组变化使旧路线失效或要求重新生成。
3. 给定分队已经确认，成员尝试更换小组时，修改被拒绝，已确认路线和分组不变；如需改变，按现有规则取消或发起新的分队。
4. 给定组织者查看分组草稿，系统显示每位成员所属的小组，供检查和确认。
5. 给定任一小组没有成员，或有成员未分组、重复分组，组织者尝试确认分队时，系统阻止确认并指出分组问题。
6. 给定每组至少有一名成员且每位成员只分到一组，组织者查看分组时，分组可供检查和确认。

## 现状事实（P0 + P1 已核）

- Living Spec `openspec/specs/splits/spec.md` 共 7 条 requirement：split draft start / boundary selection / group route generation / reunion timing check / draft detail read / confirmation / cancellation。**无「成员分组」能力**。
- `Group route generation` 现以「完整互斥 A/B 组为夹具保证的前置」为前提（`fixture-guaranteed defensive precondition`），Screen 13 场景写明「分组移动控件本期不实现」。
- 后端 `SplitDraftController` 7 个端点（`GET/POST split-draft`、`PUT boundaries`、`POST routes:generate`、`POST routes:check-timing`、`POST :confirm`、`POST :cancel`），**无分组/assignment 端点**。
- 分组来源：`SplitDraftDocument.partitionGroups()` 按成员顺序前一半 A、余下 B（design D16），在发起草稿时一次性写入文档 `groups: Map<String, List<String>>`。
- `generateRoutes` 只允许发起人（`NOT_SPLIT_INITIATOR`），按 `draft.groups().keySet()` 逐组调用 `BranchCandidateProvider`，与具体成员身份无关。
- `SplitDraftService.missingDraftParts()` 只检查 `boundaries` 与 `routes.A/B`，**不检查分组完整性**。
- 已有读面：`GET /api/trips/{tripId}/split-draft` member-only 返回 `groups`；`GET /api/trips/{id}/members` 返回成员名册（前端 `Members.tsx` 已在用）。
- 前端：`frontend/src/features/split/screen-routes.tsx` 的分组卡只显示「A 组 / N 人」，文案写明「分组移动本期不开放」；`screen-confirm.tsx` 复核屏以 memberId 原串展示 A/B 组。
- 依赖已闭合：US-038（#17）、US-039（#18）、US-042（#19）均 CLOSED 且能力已在 Living Spec；本故事不重复实现发起草稿与边界选择，只做回归。
