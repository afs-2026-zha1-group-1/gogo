## 已裁定决策

| # | 问题 | 结论 | 理由 / 相对早期草案的变化 |
|---|---|---|---|
| D1 | 变更包与分支 | 独立变更 `req-020-manage-must-do`，叠加在 REQ-019 之上；分支沿用 `feat/travel_preference`，先把 `main`（含 REQ-004）合入再作业 | REQ-019 的表与偏好页尚未合入 main，US-020 无法单独成立；同一分支避免 `registry`/`deep-dive`/`impact-brief` 三处必然冲突 |
| D2 | 持久化归属 | 复用 REQ-019 的 `member_preference`，`kind = 'must_do'`；**不新增表、不新增迁移** | 表已按 (trip, user, kind) 唯一建模，JSON payload 天然容纳条目列表；新增表会与 V4 争夺同一语义 |
| D3 | 端点形态 | 新增 `GET` / `PUT /api/trips/{tripId}/preferences/must-dos`，与 interests 端点并列 | 独立契约让 AC2/AC3 可单独断言，且不必回改 REQ-019 已评审的 interests 场景；失败互不连带 |
| D4 | 写入模型 | 整表覆盖 PUT：无 `id` 的条目新增、带 `id` 的条目原地更新、请求中缺失的条目即删除；`id` 由服务端签发并在列表内稳定 | AC2「改时间不产生第二条」靠 `id` 保真；AC3「删除」由「不在列表中」表达；单次事务、与 interests 的幂等覆盖一致 |
| D5 | 固定时间格式 | `time` 只存 `HH:mm`（严格 `^([01][0-9]\|2[0-3]):[0-5][0-9]$`），日期隐含为该 trip 的行程日期 | 夹具为单日 2026-12-05，AC 的「on 2026-12-05」由此隐含；多日行程的日期归属记为已知偏离，留给 US-031 |
| D6 | 必填规则 | `activity` 必填；`location` 与 `time` 可同时填，但**至少填一个** | 同时满足 AC1「地点与固定时间都要保存」与原型的两条校验；明确废除原型的「二选一」互斥措辞 |
| D7 | 落库时机 | 添加、编辑、删除各自立即 PUT 整表落库 | AC1「adds → saved」与 AC3「removes → no longer appears」按动作即可验；刷新页面即证据，不依赖额外点「保存」 |
| D8 | 读取范围 | `GET` 返回该 trip **全体成员**的明细，按 `userId` 升序；非成员 403 | US-031 生成需要「必做项汇总」（参考图节点 9），与 interests 的 GET 口径一致 |
| D9 | 文本规范化 | `activity`、`location`、`time` 一律先裁剪首尾空白；裁剪后空串等价于未提供 | 自由文本与受控词表不同：不裁剪会让「National Gallery 」与「National Gallery」成为两条 |
| D10 | 空列表与幂等 | `{"items":[]}` 合法，表示清空但保留行（`payload = {"items":[]}`）；重复提交同一列表幂等，`id` 不变 | 与 REQ-019 的空数组语义对齐，避免「删除记录」与「清空列表」两套语义 |
| D11 | 身份与响应风格 | 沿用 `X-User-Id`、裸 DTO 成功 + `{"code","message"}` 失败；错误 advice 与 REQ-019 的 preference 包共用 | 跟随已合并代码现实，不引入封套 |
| D12 | 页面关系 | 与 US-019 同一页 `#/trips/{tripId}/preferences`：兴趣段仍用显式「保存」，必做项段动作即保存 | 两段写入时机不同是有意设计，需在页面契约里写明，避免被误读为不一致 |
| D13 | 错误码 | 新增 `MUST_DO_ACTIVITY_REQUIRED`、`MUST_DO_PLACE_OR_TIME_REQUIRED`、`MUST_DO_TIME_INVALID`、`MUST_DO_ITEM_UNKNOWN`、`MUST_DO_ITEM_DUPLICATE_ID`；复用 `USER_REQUIRED`/`NOT_A_MEMBER`/`TRIP_NOT_FOUND`/`INVALID_REQUEST` | `code` 是契约，`message` 只是实现文本；细分 code 让负例可断言 |
| D14 | 条目 id 归属 | 服务端在 payload 内签发整数 id，取当前最大 id + 1；id **仅在该成员列表内唯一，列表清空后可复用**（P2 裁定收窄原「删除后不复用」） | 客户端 id（uuid）会把唯一性责任交给前端；按活动名定位会在同名条目上失效；持久计数器需额外 payload 字段或第二张表，对 MVP 是多余状态 |

## 解读说明

- **事实（来自 AC 与 fixtures）**：AC1 同时给出 activity、location、fixed time；AC2 的「不产生第二条」是一条列表条数断言；AC3 的「其他成员不变」是跨成员隔离断言；2026-12-05 单日行程；主线未确认。
- **事实（来自已合并代码）**：身份走 `X-User-Id`（整数，`app_user` 主键 1–5）；成员判定 `TripRepository.isMember`；错误响应 `{"code","message"}`；`@RestControllerAdvice(basePackages=...)` 按包隔离（`com.gogo.trip`、`com.gogo.invitation` 各自一份）。
- **事实（来自 REQ-019 产物）**：`V4__create_member_preference.sql` 定义 `member_preference(id, trip_id, user_id, kind, payload, updated_at)` + UNIQUE(`trip_id`,`user_id`,`kind`)；`GET`/`PUT /api/trips/{tripId}/preferences` 与页面 `#/trips/{tripId}/preferences` 由该变更建立。
- **推导（AC 未给出，不构成验收断言）**：条目 id 的具体取值、`payload` 的 `{"items":[...]}` 外层键名、`members[].mustDos` 的字段名、删除是否需要二次确认、条目数量上限。
- **已知偏离**：`time` 不带日期，多日行程无法区分「哪一天的 10:00」；这是 D5 的有意取舍，AC 的测试上下文为单日，记为后续扩展点而非本需求缺陷。
