## Verbatim story intent

**US-066.** As a traveler, I would like to log in from a dedicated login page
and continue to my dashboard or the invitation I was opening, so that I can
access shared trips under my own verified identity. Required layers:
Frontend yes, Backend yes, Database yes (read/write).

Acceptance criteria:

1. Given a signed-out traveler with no pending invitation, When authentication
   succeeds, Then a session is established and the dashboard opens.
2. Given a signed-out traveler with a pending trip invitation, When
   authentication succeeds, Then a session is established and the invitation
   preview resumes without automatically joining the trip.
3. Given a traveler on the login page, When authentication fails, Then an error
   is shown without exposing account details or granting access to private trip
   data.
4. Given a traveler who is signed out or whose session has expired, When they
   access a protected page, Then the login page opens and authentication is
   required before access is granted.

**Planning note (verbatim):** Authentication method and session design must be
agreed before implementation. The existing seeded-user / `X-User-Id` scaffold
is not verified login.

The issue's prototype screenshot is a UI reference only; the prototype's login
is locally simulated, not a production login. The local
`ui-design-reference/gogo-mvp-prototype.html` contains no login markup, so the
only login visual reference is the attachment on issue #38; Ant Design is the
repository's UI reference per `AGENTS.md` (updated 2026-11-16).

## Discovery decision

**Go** (light intake, 2026-11-16). Candidate: "add a verified login page and a
server-side session, replacing the `X-User-Id` scaffold as the identity source
for protected trip data, because US-066 requires access under the traveler's own
verified account while preserving public invitation preview and resuming it
after login."

Relation to the living spec: every current capability uses the scaffold
identity. `trips` and `invitations` will change their caller-identity contract;
`app-shell` will change its identity-switcher surface; `greeting` stays public.
This is a capability-boundary change, so the authentication method and session
design are blocking open questions, not light assumptions.
